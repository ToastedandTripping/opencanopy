## 3. wfs-client: cleanup only what this request owns, and settle the debounced-away promise

`src/lib/data/wfs-client.ts:137-143`: the `finally` of each debounced fetch deletes `pending.get(key)`, `debounceTimers.get(layerId)` and `controllers.get(layerId)` unconditionally, so an older request's `finally` deletes a newer request's entries (R2-02; reproduced by the critic in a scratch harness: 3 fetches today vs 2 fixed in the realistic case). Separately, `rejectPendingForLayer` (`:35`) never rejects: it deletes the entry and attaches a no-op catch, so a debounced-away caller's promise never settles.

Fix: guard each delete by identity (`controllers.get(layerId) === controller`, `debounceTimers.get(layerId) === timer`, `pending.get(key) === promise`); and `rejectPendingForLayer` actually rejects, with `new DOMException("Superseded", "AbortError")`. **Correction (critic r2):** not `DataFetchError("abort")`; no caller treats that as an abort. `DataLayer.tsx:1258`, the only caller, returns early only for `err instanceof DOMException && err.name === "AbortError"` and otherwise logs, clears the layer and sets status `error`; the `"abort"` kind has no producer or consumer in `src/`; the codebase convention (`forest-carbon-client.ts:209-217`, `page.tsx:225-228`) keeps aborts as `DOMException`. Mechanism: each pending entry stores the promise's `reject` beside it; `rejectPendingForLayer` calls it, then deletes the entry, both guarded by identity so a newer entry for the same key is untouched. WFS-only layers only; none public.

Tests in `src/test/pipeline/wfs-client-fetch.test.ts`:

| Scenario | Mock | Assertion | Today | Fixed |
|---|---|---|---|---|
| Realistic: C issued during B's debounce | rejects on abort | `fetch` called exactly 2 times | 3 | 2 |
| Late settle: A settles after B starts | ignores abort for A | `B.signal.aborted === true` immediately after C's call, before any timer advance | false | true |
| Same key: A in flight; B (other key) and A' (A's key) in one tick; flush; a fourth call with A's key | either | returns A''s promise | false | true |
| Debounced away: call 1 then call 2 inside the debounce, two different bboxes | either | call 1's promise rejects `DOMException` named `AbortError` | never settles | rejects AbortError |

Setups (critic r2): S1 needs request A already fetching (its debounce flushed) before B is issued; S4 needs two different bboxes, or both calls share one key and prove nothing. The leak row is revert-proved with an over-guard mutant (the finally never deletes the pending entry: 1 fetch, red), not the identity reverts.
