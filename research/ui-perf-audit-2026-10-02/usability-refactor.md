### [log] U-01 First visit to /map shows no data at all (P1, new)
Every registry entry has `defaultEnabled: false` (`src/lib/layers/registry.ts:116,247,345,402,444,579,807`), so `getDefaultLayers()` (`registry.ts:924-926`) returns `[]`. A phone visitor arriving at /map with no hash and no storage gets a dark basemap with no layer, no legend, no hint. Measured: `shots/probe-first-load-20s.png` (Pixel 7 412x839, 20 s after load): canvas saturated-pixel share 0.0 %, legend region absent, `localStorage['opencanopy-layers-v2'] = "[]"` written on first visit (so the empty state is also persisted). Data: `data/probe-first-load.jsonl`.
Fix: make the Overview preset (or `forest-age`) the default: set `defaultEnabled: true` on `forest-age` and `parks` (exactly the Overview preset, so the Overview chip lights on arrival), and stop persisting `[]` (only write storage after a user action). One-line registry change + a useLayerState test that a fresh visitor resolves to a non-empty preset.

Visible in `shots/probe-first-load-20s.png` (the "+" peeks out behind the search pill). Pinch-zoom still works, so it is degraded, not broken; a11y-wise the only zoom buttons are untappable.

### [log] U-05 Search silently does nothing on a first visit; deep-link camera and URL tracking fail on most cold loads (P0, new root cause; 08-22 P1 still open)
Measured, phone (Pixel 7), fresh context, `https://opencanopy.ca/map` with no hash: search "Port Alberni" -> 5 results in 3.9 s -> tap "Port Alberni, Municipality" -> scale bar still "100 km", hash still empty after 4 s; retry identical (`data/walk-public.jsonl` rep 0, steps after-search / search-retry; `shots/walkA-r0-02-results.png`, `shots/walkA-r0-03-after-search.png`). The map did not move. No error, no message. Geolocate (a MapLibre control, not page code) did move the map (scale "200 m"), but the hash stayed empty, so Copy link would share the province view.
Deep links (`data/probe-deeplink.jsonl`, `#lat=49.2340&lng=-124.8050&z=9.0&layers=cutblocks`): camera applied in 1 of 2 phone cold loads and 0 of 2 desktop cold loads (scale stayed "100 km" for 20 s); in every failed load a drag-pan left the hash unchanged, and in the failed phone run a search tap did not move the map either.
Root cause (code): `CanopyMap.tsx:68` `useImperativeHandle(ref, () => mapRef.current!)` copies the inner react-maplibre ref only when CanopyMap itself commits. react-maplibre creates the map asynchronously (`node_modules/@vis.gl/react-maplibre/dist/components/map.js:17-37`: `import('maplibre-gl')` then `setMapInstance`), which re-renders `<Map>`, not CanopyMap. So `page.tsx`'s `mapRef.current` stays `null` until some later page-state change re-renders CanopyMap. A first visitor with no hash and no storage triggers no such render (`useLayerState.ts:175-186` only sets state when URL/storage supplies layers), so every `mapRef.current?.…` call is a silent no-op: search (`page.tsx:421`), hot spots fly-to (`:434`), share URL (`useMapState.ts:305-307` falls back to the stale `location.href`), the deep-link fly (`useMapState.ts:169-175` polls a ref that never fills), the moveend->URL effect (`useMapState.ts:196-198` returns at mount and only re-runs on a layer change), the PDF canvas grab (`page.tsx:665`).
Fix (two steps, smallest first): (1) `CanopyMap.tsx`: delete `useImperativeHandle`; pass `ref={useMemo(() => mergeRefs(mapRef, ref), [ref])}` to `<Map>` (`src/lib/react/merge-refs.ts` already exists). react-maplibre's own `useImperativeHandle(ref, …, [mapInstance])` then fills the page ref the moment the instance exists. (2) Expose readiness as state: `onMapReady?: (map) => void` called from CanopyMap's `onLoad`; page keeps `const [map, setMap] = useState<maplibregl.Map | null>(null)` and `useMapState` / the year-sync effect key on `map` instead of reading `mapRef.current` inside an effect. Guard: an e2e that loads `/map` with no hash, searches, and asserts the hash changed (it fails today), plus a unit test that renders `CanopyMap` with a deferred mock `Map` and asserts the forwarded ref is non-null after the instance resolves.

U-05 reproduced (rep 1, `data/walk-public.jsonl`): same silent no-op on two search taps; then ONE tap on the "Logging" preset (a page-state change, so CanopyMap re-renders and the ref fills) and the identical search moved the map at once (scale "200 m" -> "1 km", hash `#lat=49.2344&lng=-124.8057&z=12.0&layers=forest-age,cutblocks&preset=threats`). That before/after is the mechanism, observed. A first visitor's natural order (search first, then layers) is exactly the failing order.

### [log] U-09 Public layers never show "Loading", "No data here" or "Zoom in": the honest status states exist only for the non-public WFS path (P1, new; the CHARTER done-1 promise is unmet on the public surface)
Code: every public data layer is tile-backed (`registry.ts:882-890` + `tileSource` on each). The only status writer on the tile path is `handlePmtilesError` -> `"error"` (`DataLayer.tsx:1104-1106`); `"loading"`, `"empty"`, `"zoom"`, `"ok"` are written only inside `loadData`, which returns at `:1144` for tile-backed layers. So `LoadingBar` (`LoadingBar.tsx`) and the legend's `LayerStatusBadge` (`MapLegend.tsx:164-185`) can never show anything but an error for the 6 public layers; and the badge renders only when the legend row is collapsed (`:232-235`) while Batch 1 made rows expanded by default, so even the error badge is hidden after the 6 s toast auto-dismisses (`StatusToast.tsx:41-47`).
Measured: `probe-status-throttled` (Pixel 7, 1.6 Mbps / 150 ms RTT, Port Alberni z12, `layers=cutblocks`): visible `role=status` text was empty in all 90 samples from 3.9 s to 155 s; the legend read "Cutblocks Cutblock (boundary)" throughout; the canvas held 0 % red until ~40 s (first PMTiles tile at 29.2 s). A phone user stares at a lit legend over an empty map for ~36 s with no signal (`shots/status-slow4g-10.png`, `-20.png`). 3.64 MB had downloaded before the PMTiles header arrived, with only cutblocks enabled (`bytesAtHeader`, `data/probe-status-throttled.jsonl`).
Fix: give PmtilesLayers its own status lifecycle: `setLayerStatus(id,"loading")` when `visible` and the layer is not yet added or its source-layer has no rendered tiles in view; `"ok"` on the first `sourcedata` for the PMTiles source after the layer is visible plus a debounced `queryRenderedFeatures({layers:[fillId]})` on `idle` (`"empty"` when zero in view, `"zoom"` below the registry `zoomRange[0]`); clear on toggle-off. Show the badge in expanded legend rows too. This is the T3 per-chip empty state from the 08-22 audit (Batch 3) and needs the R1-03/R1-05 seams fixed first (see Part 2).

### [log] U-10 If the PMTiles header takes longer than 15 s, every public vector layer is dead for the rest of the session, and the legend keeps claiming they are on (P0, new)
Code: `PmtilesLayers` (`DataLayer.tsx:408-418`) arms a 15 s timer; when it fires it removes the `sourcedata` listener and calls `onError`. Nothing ever re-arms it: the add-layers effect's deps are `[map, layer.id, layer.tileSource, layer.style]` (`:445`), none of which change when the user toggles. All six public data layers share one source, so all six timers fire together.
Measured on production code (`probe-pmtiles-timeout`, `data/probe-pmtiles-timeout.jsonl`), unthrottled network, only the header range request held back: D=8 s -> header at 16.1 s, tiles at 18.7 s, cutblocks drawn. D=17 s -> header arrived at 23.5 s (the source did load), console logged "PMTiles source for {forest-age, cutblocks, fire-history, old-growth-250, parks, tap-priority} failed to load within 15s" at 21.0 s, ZERO tile requests followed in the next 65 s, and after the user's natural recovery (remove Cutblocks from the legend, tap the Logging preset) the map was still empty: `shots/pmtiles-timeout-D17000-retoggle.png` shows the Logging chip active, a fully expanded legend for Forest Age Classes and Cutblocks, and a bare basemap. The toast "Couldn't reach BC data" listed all six layers, five of which the user never enabled, blamed the government (the failing host is OpenCanopy's own R2 bucket), and auto-dismissed at ~27 s; afterwards nothing on screen says anything is wrong.
How close real phones are: DevTools "Slow 4G" (1.6 Mbps, 563 ms RTT), `layers=cutblocks` only: the header response landed 14.07 s after style.json (`data/probe-status-throttled.jsonl`, label devtools-slow4g), with 3.57 MB downloaded before it (invisible forest-age raster overviews and basemap competing for the pipe, see 08-22 P2).
Fix: never abandon the add. Keep the `sourcedata` listener for the life of the effect; let the timer only set status `"loading-slow"` ("Still loading map data...") and keep waiting; on a real `error` event for the PMTiles source set `"error"` with a Retry action that removes and re-adds the source. Report errors only for VISIBLE layers. Toast copy: "Map tiles are slow to load" (it is our host, not BC's). Guard: a rendered PmtilesLayers test with the mock map that emits `sourcedata` at t=16 s under fake timers and asserts `addLayer` was called (fails today); the R1-13 harness in `src/test/pipeline/wfs-layers-d10.test.ts` already renders DataLayer with a mocked `useMap`.

**U-10 correction (measured after logging it):** the 15 s timer and the header request both start at the map's `load` event (`initSource` runs on `load`, `DataLayer.tsx:421-426`), so the relevant number is header *latency*, not time since style.json. DevTools Slow 4G with the Logging preset (`devtools-slow4g-logging` in `data/probe-status-throttled.jsonl`): `load` (header request) at 17.9 s, header latency 2.1 s, first tile 28.0 s, first red pixels ~41 s, `timedOut: false`. So typical slow phones do NOT hit the timeout; it takes a >15 s stall of one 16 KB request (captive portal, dead-zone handover, R2 hiccup). Severity lowered to P1: rare, but when it fires the page lies permanently. The same run adds to U-09: ~41 s from navigation to first logging pixels on Slow 4G with zero on-screen status, and the vector source is not even registered until the basemap has fully loaded (`load` at 17.9 s), which serialises the PMTiles header behind every basemap tile.

## Part 2 (draft, appended as written): refactors that remove user-visible problems and make B-E cheaper

Doctrine respected: the 09-01 refresh refused a DataLayer split and a page.tsx rewrite. Nothing below splits DataLayer or rewrites page.tsx; each item is a seam with a measured user-visible failure behind it, and each starts with a test that fails today.

### R1. The map instance is React state, not a ref read inside effects
